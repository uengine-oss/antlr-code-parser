**Feature Branch**: `006-unified-intake-classification`

**Created**: 2026-06-15

**Status**: Draft

**Input**: User description: "antlr를 유일한 입구로 만들어 업로드/경로 두 모드를 모두 받아 항상 표준 data/ 폴더를 구성. DDL/source는 내용 기반으로 분류. analyzer는 data/만 보면 끝(레거시 회귀). 경로기능은 없애지 않고 antlr로 이전."

## Overview (배경)

지금은 분석 입구가 두 모드로 끝까지 갈라진다.

- **업로드 모드**: 클라이언트가 파일을 올리면, 파서가 `source/`·`ddl/`로 저장하되 **경로가 `ddl/`로 시작할 때만** DDL로 분류한다.
- **경로 모드**: 클라이언트가 로컬 폴더 경로를 주면, 파서가 그 폴더를 **제자리에서 읽고** `source/` 세트를 만들지 않는다.

이 분기 때문에 다운스트림(analyzer)도 "data 폴더냐 / 로컬경로냐"를 따지는 분기가 곳곳(약 23곳)에 퍼졌고, 실제 사고로 이어졌다 — 경로 모드에서 **저장프로시저 `.sql`이 표 정의(DDL) 파서로 흘러갔고**, 그 파서는 프로시저 코드를 못 읽어 **분석 run 전체가 중단**됐다(산출물 0).

이 기능은 파서를 **유일한 입구**로 만든다. 모드가 무엇이든 결과는 **항상 표준 `data/` 폴더**(`source/`·`ddl/`·`analysis/`)다. 그러면 다운스트림은 "data/만 읽으면 끝"(경로 모드 이전의 레거시 형태)이 된다. 경로 모드 기능은 **없애지 않고** 그 처리를 파서로 옮긴다(로컬 파일을 `data/`로 반입). 표 정의 vs 프로그램 코드 분류는 **내용 기반**(각 파일이 무엇을 선언하는지)으로 바뀌어, 폴더를 어떻게 정리했든 프로시저 코드가 DDL 세트에 들어가지 않게 한다.

> 두 축은 분리된다 — **분류(표 vs 프로시저)는 엔진이 내용으로** 판정, **무엇을 가져올지(범위)는 호출자(프론트 스펙 014)가** 결정.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 입구 하나, 표준 출력 폴더 하나 (Priority: P1)

다운스트림 소비자(analyzer 또는 데스크톱 앱)는 업로드를 주든 로컬 폴더 경로를 주든 **동일한 표준 `data/` 구조**를 받는다. 그래서 어느 모드였는지 알 필요가 없다.

**Why this priority**: 구조적 목표. 분기 버그의 근원인 이중 경로를 없애고, analyzer가 순수 `data/` 소비자가 되게 한다.

**Independent Test**: 같은 파일을 업로드로 한 번, 로컬 경로로 한 번 입구에 넣어, 둘 다 동일한 `data/{source, ddl, analysis}` 내용을 만드는지 확인.

**Acceptance Scenarios**:

1. **Given** 혼합 파일 업로드, **When** 입구 실행, **Then** `data/source`·`data/ddl`·`data/analysis`가 채워진다.
2. **Given** 로컬 폴더 경로, **When** 입구 실행, **Then** 그 폴더로부터 같은 세 폴더가 채워진다 — "제자리·data 미생성" 특수 동작이 사라진다.
3. **Given** 두 모드 중 무엇이든 `data/`를 만들었다, **When** 다운스트림이 `data/`만 읽는다, **Then** 필요한 모든 것이 있다(입력 모드 지식 불필요).

---

### User Story 2 - 프로시저 코드는 표 정의 파서에 절대 닿지 않는다 (Priority: P1)

분석가의 소스에 저장프로시저/함수가 표 정의와 섞여 있어도, 표 정의(DDL) 세트에는 **진짜 표 정의만** 담겨야 한다. 그래야 다운스트림 DDL 파서가 프로시저 코드에 막히지 않고 run이 완료된다.

**Why this priority**: 지금 그래프를 막고 있는 바로 그 실패다. 함수 파일 하나가 전체 분석을 중단시키는 문제를 제거한다.

**Independent Test**: 일부 `.sql`은 표 정의, 일부는 함수/프로시저인 폴더를 넣어, 함수/프로시저 파일이 source(DDL 아님)로 분류되고 전체 run이 완료돼 그래프가 나오는지 확인.

**Acceptance Scenarios**:

1. **Given** `CREATE TABLE`을 선언한 `.sql`, **When** 분류, **Then** DDL 세트에 들어간다.
2. **Given** `CREATE FUNCTION`/`PROCEDURE`/`PACKAGE`/`TRIGGER`를 선언한 `.sql`, **When** 분류, **Then** source 세트에 들어가고 DDL 세트에는 절대 들어가지 않는다.
3. **Given** 분류 기준이 내용이다, **When** 프로젝트가 폴더 명명 규칙을 전혀 안 쓴다, **Then** 그래도 올바르게 분류된다.

---

### User Story 3 - 로컬 파일을 싸게 반입 (Priority: P2)

대용량 로컬 코드베이스를 분석하는 데스크톱(경로 모드) 사용자를 위해, 입구는 선택된 파일을 가능한 한 전체 복사 없이 `data/`로 반입해야 한다.

**Why this priority**: 경로 모드의 장점(업로드 왕복 없음)을 지키면서 `data/`로 수렴시킨다. 정확성과 무관한 효율 사안이라 P2.

**Independent Test**: 큰 폴더로 경로 모드 입구를 실행해, 링크가 지원되는 대상에서는 전체 바이트를 중복 없이 `data/`로 채우고, 아니면 복사로 폴백하는지 확인.

**Acceptance Scenarios**:

1. **Given** `data/`와 같은 볼륨의 로컬 폴더, **When** 입구 실행, **Then** 지원되는 경우 전체 중복 없이 파일을 반입한다.
2. **Given** 링크 불가, **When** 입구 실행, **Then** 복사로 폴백하고 정상 완료한다.

---

### User Story 4 - 한 파일이 깨져도 입구 전체가 멈추지 않는다 (Priority: P2)

분석가 입장에서, 어떤 파일 하나가 파싱/분류 불가여도 입구는 그 파일만 격리·보고하고 나머지를 계속 처리해야 한다. 전체 run을 실패시키면 안 된다.

**Why this priority**: 견고성 — 실제 레거시 코드베이스에는 이상한/옛 파일이 섞인다. 하나가 전체를 가라앉히면 안 된다. "silent fail"과는 다르다 — 건너뛴 파일을 보고한다.

**Independent Test**: 정상 파일들 사이에 깨진 파일 하나를 섞어, 입구가 완료되고 깨진 파일이 건너뜀으로 보고되며 정상 파일은 모두 처리되는지 확인.

**Acceptance Scenarios**:

1. **Given** 여럿 중 파싱 불가 파일 하나, **When** 입구 실행, **Then** run은 완료되고 그 파일은 건너뜀으로 보고된다(조용히 누락 아님).
2. **Given** 건너뛴 파일, **When** run 종료, **Then** 어떤 파일을 왜 건너뛰었는지 보고에 남는다.

---

### User Story 5 - 섞인 파일 안의 표 정의도 잡아낸다 (Priority: P3)

한 `.sql`에 표 정의와 프로시저가 함께 있을 때, 프로시저 부분 때문에 깨지지 않고 표 정의는 여전히 DDL 세트에 잡혀야 한다.

**Why this priority**: US2를 섞인 파일로 일반화. 많은 프로젝트가 파일을 단일 목적으로 두므로(드묾) 핵심 분류 위의 보강이다.

**Independent Test**: `CREATE TABLE`과 `CREATE PROCEDURE`가 한 `.sql`에 든 파일을 넣어, 표 정의가 DDL 세트에 제공되고 run이 완료되는지 확인.

**Acceptance Scenarios**:

1. **Given** 섞인 파일, **When** 분류, **Then** 표 정의 내용은 DDL 세트에 제공되고 프로시저 내용은 source로 취급된다.

---

### Edge Cases

- **빈 입력 / 파일 없음**: 입구는 빈 `data/`와 명확한 보고로 완료.
- **로컬 경로 없음/읽기 불가**: 처리 전 명시적 오류.
- **같은 파일 경로 중복**: 정해진 동작(마지막 우선 또는 거부) — 결정적이어야 함.
- **매우 큰 폴더**: 입구가 응답성 유지, 디스크 고갈 없이 반입.
- **알려진 선언과 안 맞는 내용의 파일**: source(기본)로 분류, 누락하지 않음.
- **재실행**: 매 입구마다 `data/` 전량 리셋(증분 병합 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 파서는 두 입력 모드(업로드 파일, 로컬 폴더 경로)를 모두 받아, 두 경우 모두 표준 `data/{source, ddl, analysis}` 구조를 산출해야 한다(MUST).
- **FR-002**: 경로 모드는 입력을 `data/`로 반입해야 한다(제자리 전용 동작 금지); 이후 analyzer가 `data/`만으로 동작할 수 있어야 한다.
- **FR-003**: 파일을 표 정의(DDL) vs source로 분류하는 기준은 파일명/폴더 경로가 아니라 **내용**(무엇을 선언하는지)이어야 한다.
- **FR-004**: 프로시저 객체(함수/프로시저/패키지/트리거)를 선언한 파일은 source로 분류돼야 하며 DDL 세트에 들어가서는 안 된다.
- **FR-005**: 한 파일에 표 정의와 프로시저 코드가 함께 있으면, 표 정의 내용은 여전히 DDL 세트에 제공돼야 한다.
- **FR-006**: 파싱/분류 불가 파일은 run을 중단시켜서는 안 되며, 격리하고 **보고**(어느 파일·왜)해야 한다 — 조용한 누락 금지.
- **FR-007**: 경로 모드 반입은 대상이 경량 링크를 지원하면 전체 중복 없이 가져와야 하며(SHOULD), 아니면 복사로 폴백한다.
- **FR-008**: 매 입구는 작업용 `data/` 세트를 전량 리셋해야 한다(증분 병합 없음).
- **FR-009**: AST 출력은 기존 노드 스키마대로 `data/analysis`에 기록돼야 한다(다운스트림 AST 계약 불변).
- **FR-010**: 입구는 요약 보고(DDL/source 분류 수, 건너뛴 파일 수)를 내어, 호출자가 무슨 일이 있었는지 알 수 있어야 한다.

### Key Entities *(include if feature involves data)*

- **Intake Request(입구 요청)**: 두 형태 중 하나의 입력 — 업로드된 파일 묶음, 또는 로컬 폴더 경로 + 반입할 파일 범위.
- **Classified File(분류된 파일)**: 내용으로 판정된 종류(표 정의/source)와 `data/` 내 목적지를 가진 파일.
- **Standard Data Set(표준 데이터 세트)**: 입구의 유일한 산출이자 다운스트림의 유일한 입력인 `data/{source, ddl, analysis}`.
- **Intake Report(입구 보고)**: 무엇을 분류·반입·건너뛰었는지(사유 포함) 요약.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 동등한 입력에 대해 업로드 모드와 경로 모드가 동일한 `data/` 내용을 만든다.
- **SC-002**: 저장프로시저/함수를 포함한 프로젝트가 전체 run을 완료하고 그래프를 산출한다(기존 중단이 사라짐).
- **SC-003**: 폴더 정리 방식과 무관하게, 표 정의 파일이 source로 오분류되거나 프로시저 파일이 DDL 세트에 들어가는 일이 없다.
- **SC-004**: 깨진 파일 하나가 더 이상 run을 중단시키지 않는다 — run은 완료되고 그 파일은 건너뜀으로 보고된다.
- **SC-005**: 다운스트림은 입력 모드를 모른 채 `data/`만으로 동작한다.
- **SC-006**: 큰 폴더의 경로 모드 반입이 같은 볼륨에서 전체 바이트를 중복하지 않는다.

## Assumptions

- **입구 단독 책임**: 파서가 `data/`를 만드는 유일한 곳이고, 다운스트림(analyzer)은 순수 `data/` 소비자가 된다(모드/경로 분기 제거 — analyzer 별도 스펙).
- **범위는 상류에서 결정**: 무엇을 반입할지(포함/제외)는 호출자(프론트 스펙 014)가 정하고, 이 기능은 그 범위를 받아 반입한다.
- **파서 문법 불변**: 언어 문법과 AST 노드 스키마는 바꾸지 않는다. 바뀌는 것은 입구(무엇을 어디에 담느냐)뿐이다.
- **단일 작업 세트**: 기존 전량 교체·무상태 모델과 일치 — run당 `data/` 하나, 매번 전량 리셋.

## Dependencies & Cross-Service Impact

- **↓ robo-data-analyzer**: 이 변경 후 analyzer는 `data/{source, ddl, analysis}`만 읽고 경로 모드 분기를 제거한다(동반 analyzer 스펙 필요).
- **↑ robo-data-frontend (스펙 014)**: 경로 모드 입구에 들어갈 선택 범위를 제공한다.
- **AST 계약 불변**: `data/analysis` 노드 스키마는 바꾸지 않는다(헌법 VI 충족).

### ⚠ Constitution Impact (`/speckit-plan`에서 처리 완료)

이 기능은 두 원칙을 의도적으로 개정했고, plan의 Constitution Check가 이를 기록한다:

- **원칙 III "분류 기준"** — *경로 기반*(`ddl/` 접두)에서 **내용 기반**으로 개정됨(헌법 v1.1.0, 적용 완료). 근거: 원칙 II("바이트가 진실, 호출자는 라벨을 틀린다")와 정합. 경로 규칙은 프로젝트마다 취약했고 프로시저 코드를 DDL 세트로 보내 다운스트림 중단을 유발했다. `ddl/` 접두는 역호환 힌트로 남을 수 있으나 진실은 내용.
- **원칙 III "1:1 보존"** — 섞인 파일 처리(US5)는 원본과 별개의 표 정의 산출물을 파생할 수 있다. 원본은 source에 보존, 파생 DDL 내용은 DDL 세트에 제공. 상세는 plan에서.

원칙 I(전략 자동발견), II(자동 감지), IV(전량 교체), V(스트리밍), VI(AST 계약)는 영향 없음 또는 강화됨.
