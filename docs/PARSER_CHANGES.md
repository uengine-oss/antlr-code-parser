# Java 파서 변경 사항 정리

다른 사람이 이해하기 쉽게, **문제 → 해결 → 이유** 순으로 정리했습니다.

---

## 1. code 속성 삭제 (왜 없앴는지)

### 1.1 처음 문제: code에 띄어쓰기·줄바꿈이 안 들어감

**상황**  
노드에 원본 코드를 담는 `code` 속성이 있었는데, 값이 `"publicclassFoo"` 처럼 공백 없이 붙어 나왔습니다.

**원인**  
원본 텍스트를 가져올 때 **TokenStream**을 쓰고 있었습니다.  
ANTLR에서 TokenStream은 “토큰”만 이어 붙입니다. 공백과 줄바꿈은 보통 **숨은 채널(Hidden Channel)**에 있어서, 토큰만 모으면 전부 빠집니다.  
그래서 `code`에는 토큰 텍스트만 붙어 있고, 띄어쓰기·줄바꿈은 누락된 상태였습니다.

**대응**  
TokenStream 대신 **CharStream**의 문자 범위(start~stop 인덱스)로 해당 구간을 잘라서 쓰도록 바꿨습니다.  
CharStream은 “문자 단위”라서 그 구간 안의 공백·줄바꿈이 그대로 유지됩니다.

---

### 1.2 두 번째 문제: CharStream이 긴 구간에서 터짐

**상황**  
위처럼 CharStream으로 바꾼 뒤에는 띄어쓰기는 잘 나왔지만, **긴 파일·긴 구간**을 읽을 때 CharStream 쪽에서 오류나 중단이 발생했습니다.

**원인**  
`code`에는 클래스 본문, 메서드 본문처럼 **매우 긴 문자열**이 들어갑니다.  
이걸 CharStream으로 한 번에 읽다 보니, 구간이 길어질수록 메모리·처리 부담이 커지고 문제가 났던 것으로 보입니다.

---

### 1.3 최종 결정: code를 아예 제거

**조치**  
`code` 속성과 관련 로직을 **전부 제거**했습니다.  
Java, PL/SQL, PL/pgSQL, PostgreSQL 모든 전략에서 `code` 설정을 없애고, `ParserUtils`의 `getCodeWithLineNumbers` 등 code 전용 메서드도 삭제했습니다.

**이유 (두 가지)**  

1. **기술적 이유**  
   - CharStream으로 긴 구간을 읽는 부분을 없애서, “길어서 터지는” 현상을 막기 위함입니다.  
   - TokenStream을 쓰면 띄어쓰기·줄바꿈이 다 누락되고, CharStream을 쓰면 긴 구간에서 문제가 나는 상황이었기 때문에, **원본 코드 본문을 노드에 담는 방식 자체**를 제거하는 쪽이 안전했습니다.

2. **역할·목적에 대한 판단**  
   - 이 파서가 하는 일은 **AST(구조)를 뽑는 것**에 가깝습니다.  
   - 노드마다 “해당 구문의 원본 코드 전체”를 넣는 것은:
     - 데이터가 무거워지고,
     - “구조 추출”보다 “코드 저장”에 가까워져서,
     - **파서의 본래 역할이 아니라고 보는 편이 타당**하다고 판단했습니다.  
   - 그래서 “원본 코드는 노드에 안 담고, 구조·속성만 담자”로 정리한 것입니다.

정리하면, **“띄어쓰기 누락 → CharStream 사용 → 긴 구간에서 터짐”** 이어서, **code까지 담는 건 무겁고 역할에도 맞지 않다**는 결론으로 code를 없앴습니다.

## 2. 패키지/import 이름에 "package", "import"가 붙어 나오던 문제

**문제**  
JSON에서 `packageName`이 `"packagecom.kbstar.kee.as.kr"`, import의 `name`이 `"importcom.kbstar.ksa.exception.BusinessException"` 처럼 앞에 문자가 붙어 나왔습니다.

**해결**  
이름을 자를 때 쓰는 정규식에서, 공백을 **1개 이상**(`\s+`)이 아니라 **0개 이상**(`\s*`)으로 바꿨습니다.

**이유**  
파서가 토큰을 나눌 때 공백이 빠져서 `"packagecom..."`처럼 붙어 있는 경우가 있습니다.  
공백이 없어도 "package", "import"만 잘라내려면 `\s*`를 써야 합니다.

## 3. METHOD_CALL, package, VARIABLE 플래그 등 노드·속성 추가

### 3.1 추가한 것들

- **패키지**  
  FILE 노드의 속성 `packageName` 하나로 저장 (별도 노드 아님).  
  예: `"com.kbstar.kee.as.kr"`

- **import**  
  import 문마다 **IMPORT** 노드.  
  `name`에 import 경로 (예: `"com.kbstar.ksa.exception.BusinessException"`).

- **new 인스턴스**  
  **NEW_INSTANCE** 노드.  
  타입명, 라인 정도만 저장.

- **메서드 호출**  
  메서드 호출 구문마다 **METHOD_CALL** 노드.  
  메서드 이름, 라인 등.

- **변수 초기화식 패턴을 플래그로 표시**  
  로컬 변수는 모두 **VARIABLE** 노드 하나로만 둡니다.  
  “변수 = 메서드호출” / “변수 = new 타입” 같은 건 **별도 노드(METHOD_CALL_ASSIGN)로 두지 않고**,  
  해당 VARIABLE 노드에 **속성(플래그)** 만 붙입니다.  
  - `initializerContainsMethodCall`: 초기화식 문자열에 메서드 호출 패턴(`.이름(`, `이름(` 등)이 있으면 `true`  
  - `initializerContainsNewInstance`: 초기화식 문자열에 `new 타입` 패턴이 있으면 `true`  
  판별은 **선언문 문자열을 정규식**으로 한 번만 보는 방식이라, 파서 트리 서브트리를 돌지 않아서 단순합니다.

### 3.2 왜 이렇게 했는지 (VARIABLE 플래그)

처음에는 “변수 = 메서드호출”을 **METHOD_CALL_ASSIGN** 이라는 별도 노드로 두고, 초기화식 안의 메서드 호출을 형제 노드로 붙이는 방식이었습니다.  
그러다 보니 파서 트리 서브트리 탐색, 스택 분기, 노드 타입이 늘어나서 구조가 복잡해졌습니다.

그래서 **노드 타입은 VARIABLE만 두고**, “메서드 호출/ new 패턴이 있는지”만 **VARIABLE 노드의 플래그(속성)** 로 넣기로 했습니다.  
판별도 **선언문 문자열을 정규식**으로 보는 방식으로 통일해서, 구현이 단순하고 유지보수하기 쉽게 맞춰 두었습니다.

### 3.3 왜 넣었는지

이런 노드·속성은 **추가 분석**을 하기 위해 넣은 것입니다.  
예를 들어:

- 어떤 클래스/메서드가 어떤 타입을 `new` 하는지,
- 어떤 메서드를 호출하는지,
- 변수 초기화식에 메서드 호출이나 new가 있는지(플래그로 필터),

같은 걸 나중에 코드에서 찾거나 통계 내는 데 쓸 수 있도록 하려는 목적입니다.

### 3.4 그래프·온톨로지가 아님

이 트리(노드·속성)는 **그래프나 온톨로지 형태로 시각화해서 그리는 용도가 아닙니다.**  
RDF, 지식 그래프, 온톨로지 편집기 같은 데 넣어서 “관계 그래프”로 그리는 게 아니라, **내부에서 분석·검색·리포트용**으로만 쓰는 구조입니다.  
그래서 노드 종류나 속성이 “시각화·온톨로지”에 맞춰져 있지 않고, “어떤 구문이 있는지, 어디서 뭘 쓰는지”를 찾기 편한 수준으로만 잡혀 있습니다.

## 4. 요약 표

| 구분 | 문제/요구 | 조치 | 핵심 이유 |
|------|-----------|------|-----------|
| code | 띄어쓰기·줄바꿈 누락 | TokenStream → CharStream 사용 | 공백이 숨은 채널이라 TokenStream에 없음 |
| code | CharStream이 긴 구간에서 터짐 | code 속성·관련 로직 전면 제거 | 긴 구간 읽기 제거로 안정화; AST만 담는 게 파서 역할에 맞음 |
| 패키지/import | 이름에 "package", "import" 붙음 | 정규식 `\s+` → `\s*` | 토큰에 공백이 없을 수 있음 |
| 노드 추가 | 추가 분석에 쓸 정보 부족 | packageName, IMPORT, NEW_INSTANCE, METHOD_CALL 등 추가 | 내부 분석용 (그래프/온톨로지 시각화 아님) |
| 변수 = 메서드/new | 별도 노드(METHOD_CALL_ASSIGN)로 두니 구조가 복잡해짐 | VARIABLE만 쓰고, 초기화식 패턴은 플래그(initializerContainsMethodCall, initializerContainsNewInstance)로 표시, 정규식으로 판별 | 구조 단순화·유지보수 용이 |
